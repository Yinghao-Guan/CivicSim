# CivicSim — `map` Milestone Execution Plan

**Status:** Accepted plan for the `map` milestone (written 2026-09-12)
**Relationship to other docs:** This document turns the four next steps listed in [`03-map-rendering-and-demo-area.md`](./03-map-rendering-and-demo-area.md) §5 — the same milestone as [`02-technical-stack-hackathon-mvp.md`](./02-technical-stack-hackathon-mvp.md) §17 — into ordered, independently verifiable stages. Docs 01–03 say *what* and *why*; this one says *in what order, and how we know each step is done*.

---

## 0. Scope of this milestone

Deliver exactly this:

> One real South LA neighborhood rendered in Next.js as an interactive 2.5D map, with the simulation layer's mounting point in place and proven correct.

**In scope:** demo-area definition, OSM building preprocessing, Next.js + MapLibre scaffold, clickable extruded slice, an empty-but-verified deck.gl overlay, offline tile fallback.

**Out of scope for this milestone:** synthetic agents, routing, the FastAPI backend, metrics, scenario comparison, the LLM planning agent, computer vision. Per doc 02 §17 the map comes first and AI comes last. deck.gl appears here only to prove occlusion works — it renders no real data yet.

---

## 1. Stages

### M0 — Pin down the demo area ✅ done 2026-09-12

Resolves all four open items in doc 03 §3.4. Doing this first prevents rework in the preprocessing script.

1. Confirm The Beehive's exact address — sources list both 1000 E. 60th St. and 950 E. 60th St. — and geocode it.
2. Confirm the council district against official City of LA boundaries (doc 03 believes CD 9).
3. Draw the final bounding box: ~1.5–2 km² centred on the venue, **shifted west/north to stay on the residential side and off the Alameda industrial corridor** (doc 03 §3.2 boundary note).
   *Outcome: both premises of this step turned out not to hold — the box had to grow to 3.00 km² to contain three real candidate sites, and the corridor proved 2.16 km away. See §3.2, §3.4 and §3.5.*
4. Measure what share of buildings inside the box carry `height` or `building:levels` in OSM.

**Deliverable:** the bbox coordinates, the height-coverage figure, and the district confirmation recorded in §3 of this document.

**Why item 4 matters:** it decides whether the height fallback chain produces a varied skyline or a field of identical 5 m slabs. A low figure means switching the building source from OSM to the LA County (LARIAC) dataset before M1, not after.

### M1 — Preprocessing script → `buildings.geojson`

Layout, alongside `web/` (and a later `backend/`):

```text
scripts/     preprocessing
data/        generated artifacts (committed)
```

- **Fetch:** Overpass API by bounding box, plain Python + `requests`. Deliberately **no osmium, no GDAL, no tippecanoe** — every team member can run this on macOS and on native Windows alike. Tile-based tooling arrives only if we expand to district scale (§2).
- **Attributes** per doc 02 §4.2: `building_id` (stable, generated by us), `height`, `building_type`, `facility_type`, `accessibility`, `candidate_site`.
- **Height fallback** per doc 03 §2.3.1: `height` → `building:levels × 3 m` → ~5 m. Also emit `height_source` (`measured` / `levels` / `default`) so the UI can be honest about provenance, consistent with doc 01 §13.4.
- **Candidate facilities:** tag plausible sites from OSM (`amenity=community_centre`, `amenity=library`, `leisure=sports_centre`, `amenity=school`). Mark them all; leave `candidate_site` unset until the three official candidate sites are chosen during scenario design.
- Script is idempotent and prints the output feature count and file size. At slice scale this should be single-digit megabytes — materially more means the bbox is too large.

**Done when:** `data/buildings.geojson` exists, its feature count matches the M0 measurement, and a spot check of several features shows complete attributes.

---

### M2 — `web/` scaffold and context basemap (layer ①)

- Next.js, App Router, TypeScript. Directory shape per doc 02 §8 (`components/map/`, `lib/map.ts`, `lib/types.ts`).
- MapLibre with OpenFreeMap vector tiles; pitched camera framing the M0 bbox.
- Map components use `"use client"` and are imported with `dynamic(..., { ssr: false })` (doc 03 §2.3.5). Get this right from the first commit — MapLibre and deck.gl are browser-only and SSR will fail loudly.
- Tile-provided buildings are extruded for visual context only and are **not** interactive.

**Done when:** `npm run dev` opens on a pitched view of South LA with real roads and context buildings visible.

---

### M3 — Demo slice, clickable (layer ②)

- `data/buildings.geojson` as a MapLibre `geojson` source rendered with `fill-extrusion`.
- `promoteId: "building_id"` plus `feature-state` for hover and selection highlighting (doc 03 §2.2).
- Clicking a building opens a side panel showing its attributes.
- Palette per doc 02 §6: muted/dark buildings on a warm neutral basemap. A planning tool, not Google Earth.

**Done when:** any slice building can be clicked to reveal its attributes, hover highlights, and layer ② reads as visually distinct from layer ①'s context buildings.

---

### M4 — deck.gl overlay and occlusion proof (layer ③)

- Attach `MapboxOverlay` with **`interleaved: true`** (doc 03 §2.2).
- Add one placeholder `PathLayer` routed through several buildings and a few `ScatterplotLayer` points. Their **only** purpose is to confirm the path is occluded by extruded buildings rather than floating over them.
- Once confirmed, keep the placeholders behind a debug flag rather than deleting them — they become the reference case when real simulation data arrives.

**Done when:** in a pitched view, a route passing behind a building is hidden by it.

---

### M5 — Demo-day resilience

May follow M4, but must not be forgotten.

- Export the bbox basemap as **PMTiles** into `public/`, switched by an env flag (e.g. `NEXT_PUBLIC_OFFLINE_TILES`). Layers ② and ③ are already local, so flipping the flag makes the demo fully offline (doc 03 §2.3.2).
- If pitched views with heavy overlays stutter on a high-DPI external display, cap MapLibre's `pixelRatio` at ~1.5 (doc 03 §4.3).
- Demo-day checklist: plugged in, Low Power Mode off, browser hardware acceleration confirmed.

## 3. M0 results

**Completed 2026-09-12.** All four items from doc 03 §3.4 are resolved. Doc 03 §3.1, §3.4 and §4.1 were amended to match.

Method: Nominatim for geocoding; point-in-polygon queries against two City of LA council-district layers; a single Overpass query over a 3.5 × 3.5 km survey area around the venue (22,667 buildings) then evaluated offline against candidate boxes.

### 3.1 Venue and district

| Item | Value |
| --- | --- |
| Venue | The Beehive / SoLa Technology & Entrepreneurship Center |
| Address | **1000 E. 60th St., Los Angeles, CA 90001** |
| Coordinates | **33.98530, -118.25747** |
| Neighborhood | South Park |
| Council district | **CD 9 — Curren D. Price Jr.** |

The 1000 vs. 950 E. 60th St. ambiguity resolves to **1000**: OSM carries `The Beehive` as a named `amenity=conference_centre` at that point, while 950 is a separate, unnamed address point ~190 m west — an adjacent parcel on the same street. CD 9 was confirmed independently by two City of LA boundary layers (`services5.arcgis.com/.../Council_Districts/FeatureServer/0` and `maps.lacity.org/lahub/.../Boundaries/MapServer/13`), for both address points.

### 3.2 Demo-area bounding box

| Item | Value |
| --- | --- |
| South | **33.98100** |
| West | **-118.26450** |
| North | **33.99600** |
| East | **-118.24500** |
| Size | 1.80 × 1.66 km = **3.00 km²** |
| Buildings | **4,883** |
| Venue distance to nearest edge | 477 m |

Composition: **82%** residential (`house` / `residential` / `apartments`), **6.7%** industrial or warehouse.

This box is **50% larger than the 1.5–2 km² doc 03 §3.1 originally specified**, deliberately. See §3.4 for why, and doc 03 §3.1 for the amendment. At 4,883 buildings it remains far inside the "negligible" envelope doc 03 §4.1 sets at ~10k, so the increase costs nothing in rendering budget.

### 3.3 Building height coverage

| Source | Count | Share |
| --- | --- | --- |
| `height` tag | 21,813 | **96.2%** |
| `building:levels` only | 12 | <0.1% |
| Neither | 854 | 3.8% |

*(measured across the full 3.5 × 3.5 km survey area; 95.7% within the chosen box)*

Values are fine-grained decimals — 4.0, 4.2, 3.8, 3.9 m and so on — characteristic of the LA County LARIAC LiDAR import rather than hand-entered estimates. **The §5 risk of a uniform 5 m slab field is retired: OSM is a sufficient building source and no switch to a separate LARIAC dataset is needed.** The fallback chain stays in the M1 script as a safety net, but its `building:levels` step will almost never fire.

Height distribution:

| Percentile | Height |
| --- | --- |
| p5 | 2.6 m |
| p25 | 3.6 m |
| p50 | **4.4 m** |
| p75 | 5.6 m |
| p90 | 6.9 m |
| p99 | 9.4 m |
| max | 39.0 m |

**Carry this into M3:** only 0.7% of buildings exceed 10 m and just 8 exceed 20 m. The neighborhood is almost entirely one- and two-storey, so *true-scale* extrusion will produce very shallow relief — doc 03 §1 anticipated this ("South LA is flat and low-rise so depth adds little"). M3 will need a call on whether to apply a vertical exaggeration factor for legibility, at the cost of literal accuracy. Deferred until the slice can actually be seen on screen.

### 3.4 Candidate cooling-center sites

Facilities inside the chosen box, by distance from the venue:

| Distance | Kind | Name |
| --- | --- | --- |
| 0.41 km | `sports_centre` | Mary McLeod Bethune Swimming Pool |
| 0.45 km | `park` | Mary McLeod Bethune Park |
| 1.14 km | `park` | Augustus F. Hawkins Natural Park |
| 1.38 km | `community_centre` | Slauson Senior Multipurpose Center |
| 1.41 km | `park` | James Slauson Recreation Center |
| — | `school` | 5 schools, incl. the Diego Rivera Learning Complex |

**This is what drove the box size.** Cooling-center-grade facilities near the venue are sparse: within 1 km there is exactly one (the Bethune pool). The next real candidates — the Slauson senior-centre and recreation-centre cluster — sit 1.38–1.45 km northeast, and a 2 km² box excludes them. Falling back on schools for candidates 2 and 3 would have made all three sites structurally alike, weakening the mobility-device reveal in doc 01 §5.3, which depends on candidates with genuinely different approach routes and access profiles. Enlarging to 3.00 km² buys three distinct real candidates and, as a side effect, raises the residential share from 74% to 82% while cutting industrial/warehouse from 12.0% to 6.7%.

Facilities just outside the box, available if the area is later widened: Estelle Van Meter Multipurpose Center (1.73 km south), Ascot Branch Library (1.99 km southwest), South Los Angeles Wetlands Park (1.27 km northwest).

The three official candidate sites are **not** chosen yet — that belongs to scenario design, not to M0. M1 tags all plausible facilities and leaves `candidate_site` unset.

### 3.5 Corridor check

The Alameda rail/industrial corridor lies at roughly `-118.2341`, **2.16 km east** of the venue — outside any box at this scale. Doc 03 §3.2's boundary note therefore did not constrain the outcome. The meaningful measure is the industrial/warehouse building share *inside* the box, which the chosen shape holds at 6.7%.

## 4. Cross-platform conventions

The team mixes macOS and Windows, so the build must work on both without per-machine instructions.

- Preprocessing is Python + `requests` only, versions pinned in `requirements.txt`. Nothing that needs a compiler or a system geospatial library.
- Scripts use `pathlib`; no hard-coded path separators.
- `.gitattributes` sets `text=auto eol=lf` so Mac and Windows checkouts don't produce whole-file diffs.
- **Generated artifacts (`data/buildings.geojson`, PMTiles) are committed.** At a few megabytes this is a good trade: clone-and-run matters more than a pristine repository during a hackathon.
- The one POSIX-only step is tippecanoe, needed only for the district expansion. On Windows run it under WSL; on macOS `brew install tippecanoe`.

## 5. Risks

| Risk | Response |
| --- | --- |
| ~~Height coverage in the slice is too low, so every building renders as a ~5 m slab~~ | **Retired by M0:** coverage is 96.2% with LiDAR-derived values. OSM is sufficient; no LARIAC switch needed. |
| Relief is too shallow to read as 2.5D — median building is 4.4 m and 99% are under 9.4 m | Not a data problem; a presentation one. M3 decides whether to apply vertical exaggeration once the slice is visible on screen (§3.3). |
| ~~The bbox reaches into the industrial corridor, making later synthetic-population placement unrealistic~~ | **Retired by M0:** the corridor is 2.16 km east, outside the box. Industrial/warehouse buildings inside are 6.7% (§3.5). |
| `interleaved: true` misbehaves with a particular MapLibre/deck.gl version pair | M4 is a separate stage precisely to surface this early. Fallback is `interleaved: false` — occlusion is lost and the visuals degrade, but nothing is blocked. |
